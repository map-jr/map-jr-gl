# Four reviews of the library, 2026-11-12

Four independent reviewers looked at the library on 2026-11-12. Each one had a different task and did not see the
conclusions of the others or of the person who wrote the code. This document is the combined report.

- **Who:** four AI reviewers (the same model as the one that writes the code, each started with no knowledge of the
  work).
- **Rules:** read only. Each reviewer had to say what it ran and what it only read.
- **Commit reviewed:** `60e0ba4`.
- **How sure:** a finding marked "ran" has a script that shows it. The scripts are not in the repository. The
  person who compiled this report repeated only the faults that are marked "fixed" below. Treat the others as
  reports to check, not as facts.

**What the reviewers said is good and must stay:** the state store and the one description of the main entry; the
comparison by identity and then by content; `extend` with `data`; `watchFeatures`; the warning for a query without
`await`; no CSS file; the loading design (a worker from the same origin, the fall back to the main thread, imports
that are safe on a server); no dependencies in the built files; the conformance tools that run MapLibre's own
tests, example pages and plugins; frames that cost less script than MapLibre's; a hidden layer that keeps its
tiles; memory that does not grow over create and remove.

**A suggested order of work.**

1. Faults that stop the map or mix the data of maps (the "high" rows of the correctness table below).
2. The quick wins of performance: no work for `setFeatureState` when no layer reads it; no GeoJSON in the `style`
   message when the data did not change; workers and style fetched at the same time.
3. Loud failures: a warning for each MapLibre option and layer type that has no effect; `update()` without `style`
   throws with a clear text; errors of the main entry go to the console.
4. The documents: say for each example which entry it uses; main-entry sections in `markers.md` and
   `terrain-and-elevation.md`; correct the `queryFeatures` examples.
5. Accessibility and `cooperativeGestures`.
6. A release: types in the package, source maps, a changelog, CI that stops a bad commit.

Suspected and not shown: `remove()` during the start leaves the tile workers alive (the performance reviewer
measured this: see P7); the watcher of the URL hash is installed after removal; a failed rebuild leaves old content
marked as current; `data` of the main entry can be lost when the style changes two times quickly; a listener can
run after `destroy()`.

**Design points that will make more faults:**

- State at module level in threads that maps share (`fetched` in `src/resolve.ts`, `heads`, `featureStates`,
  `globalState`). All assume one map.
- Two definitions of "loaded": the engine counts tiles that are out of date for the state of a source, but not for
  `idle`.
- The first style and later styles go through different code (`start` and `restyle`): another fetch, other error
  handling, no versions of sources.
- Queries read the bytes of a tile worker, not the tiles that are drawn, and from the next worker in turn.
- Tiles and glyph files are trusted: no limits of size or time.

**Tests that are missing** (each would have found a fault above): two maps on one page; glyph servers that answer
wrongly (added); a style with one source that fails; two `setStyle` and two `setData` calls with a slow server;
the image at `idle` after each kind of change; the fall back to the main thread; 30 queries on `idle`;
`preventDefault` on `dblclick`; hostile values for the marker colour and the credits (added); a lost context with
a style in another folder; a random-input test of the protobuf reader.

## 2. Performance

Conditions: 4 cores, no GPU (software WebGL), the liberty style, New York. Counts of messages and bytes are exact;
times are noisy. MapLibre GL JS 6.17 ran on the same page for comparison. GPU cost could not be measured.

| # | Finding | Effect | Measured? |
|---|---|---|---|
| P1 | A change of the style that has nothing to do with a GeoJSON source sends that source again and indexes it again. With 100,000 points: an 11.7 MB message, 23.4 MB to the tile workers, 548 ms of worker time. MapLibre: 8 ms. | Large, changes at run time | Yes |
| P2 | `setFeatureState` builds each tile of the source again, also with no `feature-state` in the style. 30 hover steps: 30 rebuilds, about 16 s of CPU in the workers. MapLibre: 0. | Large, hover and selection | Yes |
| P3 | Start-up is a chain: the workers start after the style and the TileJSON are there; the sprite JSON comes before the sprite image; sources are fetched one after another. | Large on slow networks | Yes |
| P4 | Each change of the style copies the whole style to each thread and compiles all layers again (100 changes: 100 messages of 40 KB and 200 of 39 KB). In one tick the changes are joined correctly, but 100 calls cost 35 ms on the page against 2 ms. | Medium | Yes |
| P5 | `addImage` with raw pixels reads back from a GPU canvas: seconds on the first call here (software GPU), 11 to 44 ms after. MapLibre: 5 ms. | Medium; needs a check on a phone | Yes |
| P6 | The image atlas never gives space back (`updateImage` fills it after about 225 updates of a 128-pixel image). Each map allocates about 20 MB of textures at once. | Medium, long sessions | Read |
| P7 | A map that is removed while it loads leaves the tile workers alive. | Small to medium (React StrictMode) | Yes |
| P8 | Load to `idle` had two modes here: about 1 s, or 3.4 to 5.8 s, with all requests done by 0.8 s. Cause not found; can be the software GPU. | Unknown | Yes |
| P9 | CI data: in Chromium on macOS the worker renderer drew 17.5 frames per second, the main thread 38.3, MapLibre 37.5. One sample on a virtual GPU. | Medium to large if real | CI data |
| P10 | One dense tile is larger than the upload budget of a frame (2.3 MB against 1.5 MB), and a tile is some hundred WebGL objects. | Medium on slow devices | Partly |
| P11 | New objects for each label in each frame; a rotation costs 11.1 ms of script against 7.2 ms for MapLibre. | Small to medium | Yes |
| P12 | GeoJSON data exists in several copies, and `setData` calls are not joined (5 calls with 100,000 points: 15.6 s of worker CPU against 8.7 s). The page is blocked less than with MapLibre. | Medium, large live data | Yes |
| P13 | State at module level in the tile workers (the same as C1). | Correctness risk | Read |
| P14 | `idle` before rebuilt tiles arrive (the same as C6). It makes benchmarks report too little. | Small | Yes |
| P15 | The size budgets have less than 1% of room and do not cover the standalone files (143 KB gzip), the files that load on demand, or the one more request from the entry to its chunk. | Small | Yes |

**Quick wins the reviewer named:** P2 step 1 (about an hour: do nothing when no layer reads the state); P5 (about
an hour); P7 (about an hour); P1 and P4 (half a day each: send data and layers only when they changed); P3 (about
a day: start the workers with the style fetch, fetch sources together, fetch the two sprite files together).

**Benchmarks that are missing:** changes at run time (paint, feature state); GeoJSON of 10,000 and 100,000
features with `setData`; a cold start with 100 ms for each request, as the median of five loads; a long session
with create and remove; a static frame, a pan and a rotation apart, also at pixel ratio 2 and 3; `addImage` and
`updateImage`.

**For the owner to check on a device:** P9 (`/bench` in Chrome on the M4, worker against main); P5 in Safari on
iOS; GPU memory after `remove()` with the worker renderer; whether P8 shows on a real GPU.

## 4. The view of a team that uses MapLibre in production

**Verdict of the reviewer:** not for a production application with custom layers, plugins and a duty of
accessibility today. Yes now for a new, flat map on a content page with a style that the team controls, where size
and the first image matter, and for the first view from a server with Nuxt.

**The three things that stop adoption:**

1. It is not a product yet: not on npm (`"private": true`), no tags, no changelog, no source maps, no statement of
   supported browsers; a build with `node build.mjs` has no type files; CI does not stop a bad commit; all history
   is two days.
2. "Drop-in" fails with no message (see row 7 of "Start here").
3. Accessibility and mobile are behind MapLibre (row 8, and no `cooperativeGestures`, no location tracking in the
   geolocate control).

**Gaps in order of how many applications they stop** (the first ten of 24): a query result used at once;
`cooperativeGestures`; custom layers; accessibility; the geolocate control (one position only); `maxBounds` in the
constructor; `locale`; `flyTo` (no arc, no `curve` or `speed`); export of the canvas with the main-thread renderer
(blank outside a `render` event, no `preserveDrawingBuffer`); the order of symbol layers.

**Other findings:**

- The documents say that each element also has its `maplibregl-*` class name. The reviewer found that the
  container, the canvas and the control buttons do not. CSS and test selectors of an application break. (Checked
  in the source after the review: controls, markers and popups have the names; the container (`maplibregl-map`),
  the canvas (`maplibregl-canvas`) and single buttons such as `maplibregl-ctrl-zoom-in` do not. The finding is
  right for those.)
- Content security policy: no `blob:` and no `unsafe-eval` are needed, which is better than MapLibre. But the
  library puts a `<style>` into the page, so a policy without `style-src 'unsafe-inline'` breaks the controls.
  There is no nonce option. A map in a shadow root gets controls with no styles.
- The server renderer fetches the style and all that it names, with no time limit, size limit or list of allowed
  hosts.
- A second `new Map` in the same container leaves two canvases (hot reload, React StrictMode).
- The size claim: the README says "about 26 KB" and counts the page script only. A usual application transfers
  about 100 KB against about 450 KB for MapLibre 6.17. The reviewer's advice: state the total, which is still 4.5
  times smaller, and state what is not there.
- The plugin results are thin in places: the scenario of `maplibre-gl-export` checks only that the control is in
  the page.
- The render tests have a floor of 800 with 818 matches, so about 18 tests can go wrong with no failure.

**Blind spots** (not in the documents, the tests or `docs/review.md`), the reviewer's list in short: accessibility
as a subject; unsupported options that are accepted in silence; reduced motion; a table of supported browsers and
a check "is supported"; `style-src` and shadow roots; source maps and errors with URL and status; scroll traps on
phones; memory on old phones; lost contexts on real devices; printing; complex scripts and vertical text (no test
shows them); pages written right to left (the scale control is wrong there); high-contrast mode; flaky networks
(retries, a label that waits for a glyph file with no end); expiry of tiles; operation of the server renderer;
the jump between the server image and the live map; hot reload; tools for migration; who owns and supports the
project; a check of the AI-written code against the sources of other projects; mid-range Android; iframes and
background tabs; alternative text for the server image; a listener that throws stops the other listeners; long
sessions; the version of the messages between the page file and the worker file; where the fonts of the demo come
from.
